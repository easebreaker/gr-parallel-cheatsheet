# 06 · EP（专家并行）

> **一句话**：EP 只切 MoE 层，通信量是 TP 的 k 倍，且**与专家数无关**。
> 它对 GR 特别友好，因为 beam 天然提供了 batch。

## 四步

```
   本 rank 的 token  x [n, d]
        │
   ① router:  score = x @ Wg        [n, E]，取 top-k
        │     → b_eff = n·k 个 (token, expert) 对
        ▼
   ② dispatch: all-to-all
        │     每个 token 发到「持有该专家的那张卡」
        │     体积 = b_eff · d · bytes
        ▼
   ③ grouped GEMM
        │     每个专家算自己收到的那批行：rows_per_expert = b_eff / E
        ▼
   ④ combine: all-to-all
        │     结果还回去，按 token 汇总
        ▼
     输出 [n, d]
```

## 三个必须记住的量

### 量 A：通信量与专家数无关

```
V_EP = 2 · B · k · d · bytes
        ↑
     没有 E
```

| E | all-to-all 字节 | 分片粒度 | 每专家行数 |
| --- | --- | --- | --- |
| 8 | 512 KiB | 2 专家/卡 | 128.0 |
| 16 | **512 KiB** | 4 专家/卡 | 64.0 |
| 64 | **512 KiB** | 16 专家/卡 | 16.0 |
| 256 | **512 KiB** | 64 专家/卡 | 4.0 |

第 2 列完全不变。**加专家只改分片粒度，不改通信量。**
这是「EP 能扩容量而不扩通信」的全部内容 —— 也是它比 TP 更适合做大模型的理由。

### 量 B：EP 的通信量是 TP 的 k 倍

```
V_EP = 2·B·k·d         V_TP = 2·B·d
V_EP / V_TP = k                  （k=8 时 8 倍）
```

**这个比值与 B 无关。** 加大 beam 不会改变 EP 相对 TP 的代价 ——
这是一个反直觉但重要的负结果。

### 量 C：每专家行数 = B·k / E

| 场景 | B | E | 行/专家 |
| --- | --- | --- | --- |
| LLM decode | 1 | 256 | **0.01** |
| LLM batch=32 | 32 | 256 | 0.25 |
| GR beam=128 | 128 | 64 | 4.00 |
| GR beam=512 | 512 | 64 | **16.00** |

低并发 LLM 的 MoE 是「每个专家算不到 0.1 行」，GEMM 效率极差。
GR 即使并发 = 1，beam 也提供了 512 的 batch。

> **这是 beam 对 EP 唯一真正的正面作用**，而且它是个**新**论点：
> 现有 EP 文献都在讨论「continuous batching 提供 batch」，
> 没人注意到 GR 不需要它 —— beam 自己就是 batch。

## 唯一的结构性风险：路由相关性

`parallel/ep_min.py` 的实测（同样的 B、同样的模型，只改输入相似度）：

| 输入 | 噪声 | 激活专家 | 专家失衡 | rank 失衡 |
| --- | --- | --- | --- | --- |
| beam（同前缀） | 0.02 | **2/16** | **8.0×** | 2.00× |
| beam（已分叉） | 0.3 | 6/16 | 7.1× | 1.82× |
| iid 独立请求 | 1.0 | 15/16 | 4.0× | 1.59× |

**只因为输入相似度不同，专家负载差一个量级。**

为什么这特别要命：

- all-to-all 的完成时间取决于**最忙的那个目的地**（max column sum），不是平均值
- beam 的 B 条假设共享前缀 ⇒ 它们路由到同一批专家 ⇒ 热专家

对比 LLM：

| | batch 的构成 | 路由 |
| --- | --- | --- |
| LLM | 不同请求，天然分散 | 相对均匀 |
| GR | 同一请求的不同假设，天然聚拢 | **相关** |

这是 GR 的 EP 与 LLM 的 EP 最关键的区别，也是唯一还没有公开工作的空白点。

## 硬约束：必须留在单机域内

12 层 MoE、bf16、d=2048、k=2：

| B | 每步总量 | 卡内 HCCS 200 GB/s | 跨机 200 Gbps |
| --- | --- | --- | --- |
| 128 | 25 MB | 0.1 ms | 1.0 ms |
| 512 | 101 MB | 0.5 ms | 4.0 ms |
| 900 | 177 MB | 0.9 ms | 7.1 ms |

跨机是 4~7 ms 的**硬增量**，直接压在 20~40 ms 的 TPOT 上（+10~30%），
且 P99 更糟。卡内只有 0.5 ms —— **差一个量级**。

> 这也解释了 Helix / MegaScale 为什么都强调 NVLink domain。

## 与 CP / TP 的分工

| 轴 | 切什么 | 通信量 | 随 B 的走势 |
| --- | --- | --- | --- |
| TP | 权重（每层都切） | `2·B·d` all-reduce | ∝ B，B 大时便宜 |
| EP | 专家（只切 MoE 层） | `2·B·k·d` 两次 all-to-all | ∝ B，是 TP 的 k 倍 |
| CP | 序列 / KV | `2·(N−1)·L·d`（ring） | **与 B 无关** |

**三个轴切的是三个不同的项** —— 这就是「混合并行是必然的」而不是「可选的」的证明：

- 权重读取 → 只有 TP/EP 能切
- prompt KV 读取 → 只有 CP 能切
- decode 的计算 → beam 能切

## 常见误解

| 误解 | 修正 |
| --- | --- |
| 「EP 的通信随专家数增长」 | 不增长。`V ∝ B·k`，与 E 无关 |
| 「EP 比 TP 省通信」 | 贵 k 倍。EP 的价值是**扩容量**，不是省通信 |
| 「beam 不影响 EP」 | beam 就是 batch。它把每专家行数从 0.01 抬到 16 |
| 「路由失衡靠负载均衡 loss 解决」 | 那影响训练；推理时的失衡是**输入相关性**造成的 |
| 「EP 可以跨机」 | 跨机会吃掉 10~30% TPOT。单机域才是 EP 的舒适区 |

# 02 · MTGR

> **一句话**：MTGR = HSTU block + 一个非因果的三段掩码。
> 而这个掩码的形状，恰好让它的 CP 比纯因果模型**更好做**。

## 论文

- *MTGR: Industrial-Scale Generative Recommendation Framework in Meituan*,
  **arXiv 2505.18654**（CIKM'25）
- 美团技术博客：<https://tech.meituan.com/2025/05/19/Meituan-Generative-Recommendation.html>

## 结构

```
 |<--------- 静态 S --------->|<-- 动态 R -->|<- 候选 K ->|
   U(用户画像)  S(历史行为)      R(当日实时)     C/I(曝光样本)
        │            │               │              │
        └────────────┴───────────────┴──────────────┘
                          │
                    Group-LayerNorm        ← 不同语义域各自归一化
                          │
                  HSTU block × L            ← 与 01 完全相同
                          │
                  逐候选打分
```

## 三条掩码规则（论文原文）

1. **静态段对所以 token 可见**
   U 和 S 来自聚合窗口之前，不会泄漏未来信息。

2. **实时段内部因果**
   只能看更早发生的实时行为。

3. **候选段只看自己**
   候选之间不能互相偷看。

```
        S(0..95)      R(96..119)   C(120..127)
   ┌──────────────┬───────────┬──────────┐
 S │ 全可见 (方阵) │   全可见   │  全可见   │
   ├──────────────┼───────────┼──────────┤
 R │    全可见     │  因果三角  │  不可见   │
   ├──────────────┼───────────┼──────────┤
 C │    全可见     │ 按时间戳   │ 只有自己  │
   └──────────────┴───────────┴──────────┘
```

**第 3 条最容易被忽略**：如果不隔离候选，同一批曝光里后发生的那个会把答案泄漏给
先发生的那个 —— 离线 AUC 虚高、上线崩掉。这是推荐系统独有的坑。

## 为什么要动态掩码

论文里说的场景：一次请求聚合「用户一天」的数据，但候选曝光发生在一天中的不同时刻。

- 朴素因果掩码：候选按时间倒序排，看起来「更晚的候选能看到更早的行为」—— 看起来对
- 实际上：某些候选发生在某些实时行为**之前**，因果掩码会让它看到未来的行为

所以他们用**时间戳 + 因果**双条件，而不是单纯的位置因果。这需要每个候选有自己的时间戳，
掩码因此是**动态**的（依赖样本内容，不是固定的三角）。

## 成本：闭式 pair 数

```
    pairs = S²  +  [P(P+1) − S(S+1)]/2  +  K·(P+1)        P = S + R
            ↑         ↑                      ↑
         静态方阵   实时因果三角         候选看整段前缀 + 自己
```

这个式子可以**逐位验证**（`models/mtgr_min.py` 里 `assert` 了）。

实测的密度（pairs / n²）：

| 配置 | pairs | 密度 | 静态占比 |
| --- | --- | --- | --- |
| S=1000, R=60 | 1.07 M | **0.938** | 93% |
| S=2000, R=100 | 4.22 M | **0.950** | 95% |
| S=4000, R=60 | 16.3 M | **0.983** | 98% |

> **密度 0.94~0.98 意味着：MTGR 的注意力矩阵几乎是一整个方阵。**
> 这是它和纯因果模型（密度 0.5）最本质的差别。

## 并行含义

| 轴 | 结论 | 原因 |
| --- | --- | --- |
| **CP** | **有对象，而且比纯因果好做** | 静态段是方阵 ⇒ 失衡 1.00 |
| EP | 有条件 | Scaling User Module 是 MoE，但 GLN 的归约轴需核实 |
| TP | 可以 | 常规 |
| beam | 无关 | 判别式（它是 ranker，不是 generator） |

### 为什么「方阵更好切」

把长度切成 N 块，看每块的工作量：

| 掩码 | 每块工作量 | 失衡度 |
| --- | --- | --- |
| 方阵 | 全部相同 | **1.00** |
| 因果三角 | 第 r 块 ∝ r | **2 − 1/N**（N=8 → 1.87） |
| zigzag 配对 | 相同 | 1.00（代价：重排 kernel） |

静态段占比 93%~98% ⇒ 整段的失衡度被拉向 1.00，**而且不需要 zigzag**。

> 这解释了 `gr-cp-cost-model` 里那条预言：MTGR 上「2·CP mini-chunk +37%」的收益
> 应该会**缩水** —— 因为在方阵主导的结构里，配对本来就没多少可配。

## GLN 的并行含义

Group-LayerNorm：不同语义域（U / S / R / C）各自算均值和方差。

- 只需**组内**统计量 ⇒ 是 token-wise 的
- 与 CP 的序列切分正交：切到哪一段就只用那一段的统计量，不跨卡

只要保证「每个 token 只用自己的组内统计」，GLN 就不会成为 CP 的新同步点。
**例外**：如果某个组的 token 被切到了两张卡上，组内均值就必须跨卡归约 ——
这是一个需要核实的实现细节（MTGR 的 GLN 归约轴）。

## 常见误解

| 误解 | 修正 |
| --- | --- |
| 「MTGR 和 HSTU 一样，所以 CP 结论一样」 | 掩码不同 ⇒ 失衡度不同。MTGR 更好切 |
| 「动态掩码 ⇒ 掩码必须跨卡传递」 | `cp_q` 下每卡自己那段掩码自己知道，零传递 |
| 「候选只有几十个，切它没意义」 | 对，候选段不切。切的是静态段 |
| 「静态段对所以 token 可见 ⇒ 必须复制」 | 复制的是 KV（`cp_q`），这正是零通信的做法 |

# 07 · beam（搜索宽度并行 / 执行优化）

> **一句话**：beam 的三次提速分别消掉「KV 冗余读取」「KV 重排」「host 同步」。
> 但它不是一个高天花板的并行轴 —— 反算出来只有 1.3~2.2×。

## 三种摆法

```
(0) 朴素：beam 摆 batch 维

    q = [B, d]                      KV = B 份，各 [P+t, d]
    ┌──────┬──────┬──────┬──────┐
    │beam0 │beam1 │beam2 │beam3 │   → prompt KV 读 B 遍
    │ P+t  │ P+t  │ P+t  │ P+t  │
    └──────┴──────┴──────┴──────┘

(1) Tree Attention：beam 摆序列维

    q = [B, d]                      KV = 1 份，[P + B·t, d]
    ┌──────────────────────────────┬─────────────────────┐
    │  prompt (只一份)              │ step0:B │ step1:B  │
    └──────────────────────────────┴─────────────────────┘
                     ↑ 掩码限制「每个 token 只看自己的祖先」

(2) 静态 KV + 掩码代替重排

    预分配 [P + B·(N−1)]
    剪枝时不动 KV，只改掩码
```

## 实测正确性与字节账

`parallel/beam_min.py`（B=4, P=8, 3 步）：

| | naive | tree |
| --- | --- | --- |
| 输出 | — | 与 naive `max_err = 1.1e-16` |
| KV 读取 | 108 行 | 36 行（**3.0×**） |

tree attention **不是近似**，它只是把同一批 `(query, key)` 对换了个布局。

放大到真实尺寸（B, P=1024, d=2048, 3 步）：

| B | 静态 KV 分配 | vLLM 重排（最坏） | 树掩码 | 重排/掩码 |
| --- | --- | --- | --- | --- |
| 128 | 10.0 MiB | 1024 MiB | 0.17 MiB | 5958× |
| 512 | 16.0 MiB | 4096 MiB | 1.25 MiB | 3277× |
| 900 | 22.1 MiB | 7200 MiB | 3.20 MiB | 2253× |

**掩码比 KV 重排小两三个数量级。** 所以「不搬 KV，改掩码」是这一层的全部收益。

## 华为那张表（910B4，OpenOneRec-1.7B，L=1024）

| 方法 | BW=128 | BW=512 |
| --- | --- | --- |
| vLLM | 244.7 ms | 1989 ms |
| 自研（Tree Attn + TorchAir） | **59.1 ms** | **79.0 ms** |
| 加速比 | 4.1× | **25×** |

同一篇里更关键的三个数（用来反解成本律）：

| BW | TPOT（NPU 时间） |
| --- | --- |
| 128 | 14.2 ms |
| 512 | 24.0 ms |

**BW 涨 4×，时间只涨 1.69×。**

## 成本律：t(B) = F + a·B + b·B²

三项的来源：

| 项 | 来源 | 与 B 的关系 |
| --- | --- | --- |
| `F` | 权重读取、prompt KV 读取（**B 个 query 共享一次读取**）、launch | 常数 |
| `a·B` | QKV 投影、FFN、LM head | 线性 |
| `b·B²` | tree 内部 `B` 个 query 对 `B·t` 个新 KV 的交互 | **二次（beam 独有）** |

用两个公开点反解，取 `b ≥ 0`：

```
F = 10.93 + 65536·b  ≥ 10.93 ms

B=128 天花板 = 14.2 / 10.93 = 1.30×
B=512 天花板 = 24.0 / 10.93 = 2.20×
```

**这就是「无限张卡也拿不到」的上限。**

### 为什么 F 与 B 无关：关键的一行

tree attention 下，一次 decode 的 KV 形状是 `[P + B·t, d]`，
而 query 有 `B` 个 ⇒ **同一份 KV 被 B 个 query 共用一次读取**。

```
KV 读取量 ∝ (P + B·t) · d · 层数        没有独立的 B 因子
```

对比 vLLM（beam 摆 batch 维）：

```
KV 读取量 ∝ B · (P + t) · d · 层数      有 B 因子
```

⇒ vLLM 在 BW 128→512 时从 244 ms 涨到 1989 ms（**8.1×**，接近线性），
华为从 59 ms 涨到 79 ms（**1.3×**）。

> **华为的 25× 不是把计算做快了，是把 B 从 KV 项里消掉了。**

## 所以 beam 并行的天花板

```
t(B, N) = F + a·B / N    →  N→∞ 时  →  F
```

计算随 N 线性缩，**KV 读取完全不缩**。这不是实现问题，是结构问题。

和你 CP 那边「CP 输在不能摊薄」是同一个机制，只是换了变量。

## 三层各自消掉什么

| 手段 | 消掉的东西 | 量级 |
| --- | --- | --- |
| Tree Attention | prompt KV 被读 B 遍 | **B 倍** |
| 静态 KV + 掩码 | 每步 KV 重排 + PagedAttention 元数据 | 1~2 个数量级 |
| 循环展开 + 图 | 每步一次 host 同步 | 取决于步数 |
| SID 受限解码 | 在全词表上算 logits | 21.5×（8192 vs 176384） |

**注意顺序**：华为那篇的标题就是结论 ——
*Optimize the Cob, Then the Kernel*。先把整条流水线理顺，再优化单个 kernel。
他们的 attention kernel 其实**比自研 baseline 慢**（4.4 ms vs 3.7 ms），
但因为省掉了 KV 重排，端到端反而持平或更快。

## 空白在哪

| 位置 | 状态 |
| --- | --- |
| 单卡 tree attention / 静态 KV / 图展开 | **已被占满**（华为 2026-11） |
| beam 作为分布式轴（GR） | **空白**（One Global Beam 只做了组合搜索，不是 DNN） |
| beam × EP 的路由相关性 | **空白** |
| beam 的成本律（三项式） | **空白**（只有 `L≈D·f(B)` 这类口头经验） |
| beam 让 CP 重新有对象（q=B） | **空白** |

## 常见误解

| 误解 | 修正 |
| --- | --- |
| 「beam 越大越慢，线性」 | 实测 4× beam 只涨 1.69×；二次项在 GR 的 3 步里可能根本不主导 |
| 「beam 是解码参数，不是并行维」 | 在 GR 里它是主维度，B 从 128 到 900 |
| 「多卡能线性加速 beam」 | 天花板 1.3~2.2×（由 F 决定），加卡不能突破 |
| 「tree attention 有精度损失」 | 无。`max_err = 1e-16`，它是精确的布局变换 |
| 「优化 attention kernel 最有效」 | 华为的 kernel 更慢但端到端更快 ⇒ 瓶颈不在 kernel |
